# F 系列记忆系统的上下文预算（设计约束建议）· 2026-11-09

起因：跨 Agent 共享记忆如果做成"每个 Agent 把项目记忆读进上下文"，就是几个 30 万上下文互相叠加。一卡一进程省下来的东西，在这里会全部吐回去。

## 一句话原则

**记忆不进上下文，检索结果才进。** 上下文里只放这次任务用得上的几条，而且要压到一句话；完整内容按需再读。

## 五条硬机制

1. **注入预算**：每次向 Agent 注入记忆时有 token 上限（建议 1500，可按项目调）。超限按重要度截断，并且明确告诉 Agent「还有 N 条未注入」，不许静默丢。
2. **分层加载**：先给目录（每条一行：id、类型、一句话、可信度、更新时间），Agent 需要哪条再按 id 取全文。检索命中 8 条不等于注入 8 条全文。
3. **条目带版本和内容 hash**：Agent 手里的摘要带 hash，写回时凭 hash 判断自己是否过期，不需要为了"确认没变"把全文重读一遍。
4. **写回只写增量**：新增长条、修正（指向被改条目的 id + 新内容）、作废（id + 理由）。禁止整份记忆重写，那是把磁盘当上下文用。
5. **可度量**：记录每次注入的 token 数、注入后被实际引用/使用的比例。使用率长期低于 30% 说明检索或重要度打分有问题，不是"多给点更保险"。

## 与 F 系列条目的对应

- F03（规范实体、版本、来源、重要度、可信度、有效期）：这些字段就是注入排序的依据，必须做全，缺了就只能按时间排。
- F04（按项目/角色共享、私有授权）：授权要在检索里过滤，不是取出来再删——否则私有记忆已经进了上下文。
- F07（带版本检查、幂等键的并发 API）：返回增量，返回带 hash 的摘要，不返回整库。
- F08（授权召回、任务上下文注入、写入提案）：注入就是上面第 1、2 条；提案就是第 4 条。

## 反面做法（要写进契约的禁止项）

- Agent A 把 Agent B 的会话上下文读进来。那是两份 30 万相加，不是协作。
- 把整个项目的记忆序列化成一段 prompt 塞进去。
- 注入时不告知截断，让 Agent 以为看到的是全部。
- 为了"避免不一致"每次都全量重读记忆。

## 多 Agent 协作的正确形状

共享的是**存储**，不是上下文：任务板写"谁在做什么、做到哪"，记忆库存"结论和依据"，Agent 之间只通过这些结构化记录交换，一轮只取自己需要的那一小片。

## 省钱以外的好处

这套形状顺带解决三个已有问题：私有记忆不会因为"先取后滤"泄漏；版本 hash 让并发写冲突可判定；注入量稳定后，成本不再随项目记忆增长而线性上涨。

## 本地小模型的落点

- embedding 检索：本地跑（bge-m3 / Qwen3-Embedding-0.6B），每轮检索不花钱
- 摘要压缩到一句话：4B 级别够
- 重要度打分：分类器或 1.7B，比让大模型现算便宜一个数量级
