日期：2026-10-31（Asia/Shanghai）
状态：新增需求与契约设计，尚未接入执行器。已确认来源类别：用户、Agent、系统自动生成，并支持混合来源。

## 1. 已确定的新增要求

| ID | 要求 | 目标行为 |
|---|---|---|
| T25 | 执行问题与解决方案进入 Wiki | Agent 遇到的问题、尝试、解决方法与验证证据形成可复用页面 |
| T26 | 产出手册与方法进入 Wiki | 产出物关联使用说明、适用方法、版本和常见问题 |

这批要求增加知识回流闭环：执行产生经验与产出 → Wiki 整理 → 跨 Agent 检索与复用 → 记忆只保留经规则允许的摘要和稳定方法，链接回 Wiki 证据。

## 2. 三类知识页面

### 2.1 问题与解决方案（troubleshooting）

建议记录：标题、症状/错误、发生任务、软件/环境/版本、影响范围、复现条件、根因及其验证状态、尝试过的方法与结果、有效解决步骤、验证证据、回退方式、已知限制、关联产出与来源。

状态建议：open / workaround / verified / superseded。未解决的问题也保留为 open；尝试过的方案需区分 failed / unverified / verified，不把“Agent 建议尝试”写成“已经解决”。

相同项目与适用环境下的问题可通过指纹关联已有页面，补充本次任务和新证据。不能仅因错误文本相同（如 timeout）就自动合并根因不同的问题。

### 2.2 产出物使用手册（usage_guide）

建议记录：产出物名称、稳定 ID/位置、版本或内容哈希、用途、适用人群、先决条件、启动/安装、操作步骤、输入输出示例、配置/参数、结果检查、常见错误、限制、维护与升级方法、相关问题页面。

手册绑定明确的产出版本；产出更新后补相应版本的说明，旧说明可追溯。找不到产出、没有运行证据或步骤尚未验证时明确标注，不编造安装命令或成功输出。

### 2.3 可复用方法（procedure）

将解决方案中跨任务可复用的部分整理为方法：适用条件、目标、步骤、验证标准、不适用条件和案例。与具体问题页、手册互链；不要把单次环境下成功的方法泛化为所有环境都成立。

目录建议为 wiki/troubleshooting、wiki/guides、wiki/procedures；需要接入项目 schema/页面类型/索引与图谱，不能只新增目录后依赖模型猜测路由。

## 3. 自动回流流程

1. 执行器捕获 taskId、工具调用结果、错误/修复事件、验证结果及产出清单；按已有权限与数据规则筛选可入库内容。
2. 任务结束、阻塞形成有价值记录、验证通过或产出版本变化时，生成相应 Wiki 草稿或修订。
3. 检索同范围已有问题、手册和方法，确定新建还是版本化更新；使用幂等键避免重复页。
4. 把真实证据与模型推断分开：执行器提供来源/验证事件，模型负责整理文字，不能自行证明自己的方案已有效。
5. 沿用既有记忆/Wiki 发布策略与权限：低风险文档可按规则生效；核心规则变更、权限扩展和有争议内容进入既有提案处理流程。
6. 提交 Wiki 版本、索引更新事件、来源与任务关联；记忆服务按其政策提炼引用，不直接提升为高可信恒星。
7. 记录写回结果。Wiki 写入失败可独立重试，不重新执行原始任务；原任务结果与“说明文档待完善”分别表达。

问题/手册是正文知识；完整运行日志、实时进度、重试/取消操作仍只在统一任务管理器。业务页面保留问题内容、方法和产出引用。

回流与文档纠错纳入现有 wiki_maintenance 分类，关联原任务作为子任务；不增加第四个任务标签。

## 4. 来源标识：谁写，与依据什么，分开记录

### 4.1 页面与版本两个层级

- 页面的首次创建者、首次建立时间保持稳定。
- 每个版本记录实际作者、有效权限身份、工作角色、工具/调用入口、关联任务、修改时间与原因。
- contributors 记录贡献者集合；其他作者补充或修订后，不把页面整体来源改成“最后编辑者”。
- sourceRefs 记录原始资料、任务证据、产出物与关联 Wiki 版本，独立于作者身份。
- 正文来源 originKinds 记录 user / agent / system 的实质贡献集合：单一来源对应单一徽标，多于一种显示 mixed（混合来源）。保留 initialOrigin 与每个版本的 originKinds。
- system 表示受控的内部自动生成流程，例如根据结构化执行事件生成正文；它是来源/内部主体类别，不新增第四种人员或 Agent 登录角色。
- 系统更新索引、时间和其他元数据不构成正文创作，不将所有页面自动变成 mixed。用户仅确认 Agent 草稿时标“用户已审核”，不冒充用户编写。
- 外部原始资料继续作为 evidence/sourceRefs 记录；导入者身份与原资料作者分开，外部资料不是本轮新增的第五种创作身份。

| 徽标 | 判定 |
|---|---|
| 用户 | 正文实质来源为人员编写；admin 亲自编写也属于人员贡献 |
| Agent | Agent/LLM 生成实质内容，记录具体 Agent、任务和执行身份 |
| 系统生成 | 无 Agent 正文创作的受控程序、规则或模板从结构化数据生成正文 |
| 混合来源 | 用户、Agent、系统中至少两类有正文实质贡献；展开查看各方及版本 |

自动流程调用模型生成正文时仍记录 Agent 内容贡献，不能只因调度器是系统而把 Agent 生成内容伪装成纯系统生成。

### 4.2 可信来源由执行器/服务端生成

createdBy / actorPrincipalKind（user/agent/system）/ actorPrincipalId / effectivePrincipalId 等字段来自已认证上下文，不采信模型生成的 frontmatter 或调用者任意传入的“我是用户”。

Agent 即使获授权切到某个人员权限身份，实际作者仍标为 Agent，并注明其有效身份和工作角色。用户通过 UI 确认草稿的行为记录为“用户审核”，不抹去 Agent 的原始生成贡献。

管理员属于权限角色；管理员亲自编辑的内容在作者类别上仍是人员贡献。作者类别不能直接替代真实性或验证状态。

### 4.3 建议 UI

Wiki 页标题附近展示：

```text
Agent 来源 · Atlas
以「项目审阅身份」/「研究员」编写
建立时间 / 最近更新 / 关联任务
验证状态：已在所述环境验证
```

元数据区继续显示逐来源原始文件入库时间、证据与原始资料。版本历史展示“谁，以什么身份，改了什么”。列表和星图可按已确定来源筛选，颜色/徽标的来源语义与业务分类图例分开。

外部资料由用户导入、Agent 生成摘要的情况，应记录为“导入者 + 生成者 + 原始资料引用”；页面来源徽标按实质贡献记录确定；用户导入行为、原始资料作者与 Agent 摘要贡献分别展示，不覆盖彼此。

## 5. 规范数据建议

WikiPage：id、pageType、knowledgeBaseId、projectId、title、domainIds、createdAt、createdBy、currentVersion、contributors、sourceRefs、artifactRefs、taskRefs、validationStatus、visibility/ACL。

WikiRevision：pageId、version、expectedBaseVersion、contentHash、actorPrincipalId、actorPrincipalKind、effectivePrincipalId、workRoleId、tool、taskId、reason、evidenceRefs、validatedFor、createdAt。

EvidenceRef：任务/工具事件/源文档/产出物/页面版本等明确来源。ArtifactRef：产出 ID、版本/哈希、位置和访问范围。身份元数据由后端写入，Markdown 可导出其投影。

跨 Agent 并发修订仍采用 expectedVersion、409 冲突与幂等键；写回服务与普通 Wiki 编辑使用同一权限和版本入口，不能从 Agent 特殊通道绕过检查。

## 6. 与记忆和星图的联动

- 问题发生属于情景/工作记忆；验证后稳定的方法可成为程序记忆；长期归纳可成为反思记忆。
- 问题页、方案页、产出和手册形成 typed relations，例如 documents、resolves、verified_by、derived_from、supersedes。
- Wiki 关系模式显示知识页面和文档关系；记忆模式显示获准记忆及其引用，不无条件把所有任务日志变成记忆节点。
- 候选方案不因被多 Agent 转述而成为恒星；“已解决”需有真实验证信息；单次成功也不直接等于跨任务高适用性。
- 记忆详情可追到问题/手册的具体 Wiki 版本；Wiki 修订后，依赖记忆进入重新验证或版本更新。

## 7. 共享、发布与 Obsidian

来源任务、产出物与原始资料的权限共同约束回流内容；私有任务经验不能因写进项目 Wiki 自动扩大共享范围。跨范围发布需要明确授权或经确认的脱敏版本。

已有 Obsidian 约定保持不变：只向 Vault 专用记录目录回传关联 Wiki/手册结果，不修改原笔记。原任务的 Wiki 回流结果可以补入其结果清单；回传故障与 Wiki 写回故障分别重试。

## 9. 验收

1. 失败后没有解决的问题进入 open；有验证的修复记录步骤和证据；失败尝试不被写成成功。
2. 产出有对应版本的使用手册和适用方法；产出更新可定位需要更新的手册。
3. 两个 Agent 遇到同类问题可复用已有知识，重复写回不创建重复页；不同环境/根因保留差异。
4. 页面创建者、版本作者、贡献者和证据能分别查看；Agent 切权限身份不伪装成人员作者。
5. 用户审核 Agent 草稿后保留两方各自贡献；系统生成和混合来源标签正确；机械元数据更新不会使页面误变为混合。
6. 私有经验不会泄漏到共享 Wiki/星图/召回；模型生成的来源字段不能覆盖认证身份。
7. 写回失败可独立重试，原执行结果不丢失，也不重复运行原任务。
8. Wiki 的问题/手册/方法、记忆引用、图谱与 Obsidian 回执可追到同一任务和产出版本。
