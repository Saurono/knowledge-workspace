# M10-C4 读路径评估（2026-11-10 16:58，实测）

环境：Windows / win32，Node v24.22.2，WAL，`service.sqlite`。夹具与写侧基准一致：body 300 字符、每条 5 个 revisions、100 / 500 / 1000 条记忆。A/B/C 各预热 2 次、采样 30 次；D 为 8 个并发读、20 轮（同进程内同步 SQLite 并发调用，不代表 8 线程真并行）。

- A = `repository.get(project,"workspace","default")`，现读路径：整份 JSON 读 + parse
- B = `repository.memoryRows(project)`，主表全扫（含 `record_json` parse）
- C = 主表投影查询（同库只读连接）：`SELECT id,title,status,version,updated_at ... ORDER BY updated_at DESC,id LIMIT 200`
- D = 8 并发跑 A / C

## 结果

| 记忆数 | A p50/p95 ms | B p50/p95 ms | C p50/p95 ms | D-A p50/p95 ms | D-C p50/p95 ms |
| --- | --- | --- | --- | --- | --- |
| 100 | 2.4 / 3.4 | 2.5 / 3.4 | 0.1 / 0.2 | 10.0 / 18.4 | 0.3 / 0.6 |
| 500 | 11.2 / 13.6 | 15.1 / 17.6 | 2.1 / 2.2 | 55.5 / 93.5 | 9.4 / 19.5 |
| 1000 | 22.9 / 27.6 | 29.8 / 33.5 | 3.6 / 4.0 | 111.6 / 190.1 | 17.5 / 29.4 |

平均返回字节数：A 625 KB / 3.1 MB / 6.3 MB；B 741 KB / 3.7 MB / 7.4 MB；C 10.9 KB / 22.2 KB / 22.2 KB。并发 160 次调用全部成功，无失败。

## 结论：不整体切；只给列表页加投影查询

依据两个数：

1. **B 比 A 慢**（1000 条 p50 29.8 vs 22.9 ms）。主表整扫省不掉 `record_json` 的 parse，还多搬一份 `content`，所以"把读路径整体换成主表"没有收益，只有风险。
2. **C 比 A 快 6–17 倍，字节少 280 倍**（1000 条 p95 4.0 vs 27.6 ms；6.3 MB → 22 KB）。列表页只要 id/标题/状态/版本/时间，走投影查询是对的。

要动的最小面（**只列，不实现**）：

- `repository` 加只读 `listMemorySummaries(projectId, {limit, after})`（投影 + 游标分页）与 `getMemoryRecord(projectId, id)`（单条完整记录）。
- `SharedRepository` 端口加这两个方法；`createAuthorizedRepository` 逐条套用现有可见性规则（列表只返回调用方可见的记忆，计数由授权层决定，不能先全量再前端过滤）。
- `visibleWorkspace` 契约不动：整份 workspace 读写仍走 JSON，主表只是索引/投影。

反转条件：如果哪天记忆平均正文涨到几 KB 级、或者 1000 条时 A 的 p95 超过 50 ms，再看要不要切完整读；现在没到。

## 一个必须记住的事实

`memoryRows` 的 `record` 是从 `record_json` parse 出来的 —— **主表读路径并不省 parse**。它的价值在"只搬一条/一列"，不在"不复原对象"。别把 B 的收益说大。

注：`memories` 表当前没有 `importance` 列，所以 C 的投影不含它；列表按重要度排序需要先加列（另开卡，别在这张卡里加迁移）。
