# 使用手册：用户 / 管理员 / Agent / 本地文件

最后核对：2026-11-10 21:20，按本轮代码核对

核对日期：2026-11-10；分支：`codex/knowledge-workspace-v0.1`。本文按当前源码描述使用行为，不代表部署验收。共享 Web、桌面本地 API、Vault 连接器是不同入口，不能混用凭据或假定能力相同。安装、升级、备份和故障处理见同目录 `runbook-20261110.md`，本文不重复运维步骤。

## 1. 普通用户（user）

### 项目与 Wiki

- 共享网页顶部“当前项目”选择已有项目；填写“新项目名称”，点“创建项目”。实际创建还受全局账号权限控制，不是每个项目 viewer 都能创建。证据：`src/web/workspace.tsx` 的项目表单、`server/http.ts` 的 projects 分支。
- 在“Wiki”页签点“新建 Wiki”，修改默认路径 `wiki/queries/new-page.md`，填写“Wiki 正文”，点“保存 Wiki”；点左侧已有路径可读取、编辑该页，已有页路径不可直接改名。正文下方有 Markdown 预览，“复制草稿”用于另存当前文本。没有 `wiki.write` 时写入控件禁用。证据：`src/web/workspace.tsx`。
- 读取页会保存资源 revision；已有页保存携带 `If-Match: "v<revision>"`，新建用 `If-None-Match: *`。版本不一致返回 409，界面显示错误，保存失败不会清掉草稿或标记已保存；可先“复制草稿”，再点“刷新资源（放弃未保存内容）”，读取最新版后人工合并。当前没有自动合并冲突界面。证据：`src/modules/service-api/application/client.ts`、`server/http.ts`、`src/web/workspace.tsx`。
- 修改正文后，切换项目/身份前有确认放弃草稿的提示，关闭或刷新浏览器有 `beforeunload` 提醒。不要把它理解成所有点击都有保护：当前“新建 Wiki”和点击另一页的处理直接替换编辑状态，使用前请先保存或复制草稿。证据：`src/web/workspace.tsx` 的 `canLeave`、`markDirty`、页面点击处理。

### 文档入库

在“文档”页签选择“上传原始文档”（需要 `documents.write`），共享服务默认上限 16 MiB。界面明确写着“上传仅表示服务已接收原始文件；解析、入库和索引不会被标为已完成”。列表中的“已接收”、字节数、接收时间仅证明收件；“来源入库”和“当前修订入库”的未知值不能当成成功。证据：`src/web/workspace.tsx`。

需要核对处理阶段时，可读取项目下 `GET /documents/{id}/ingestion` 的 checkpoint 与 summary，或 `GET /documents/{id}/receipt` 的处理回执；两者要求 `documents.read`。共享网页列表当前没有完整的阶段进度操作台，不能仅凭上传成功认定已可检索。证据：`server/http.ts`、`src/modules/ingestion/domain`、`src/modules/obsidian/application`。

### 知识领域

“知识领域”页签中用领域编辑器新增/删除标签；有 `domains.manage` 才可管理。在 Wiki 或文档列表条目旁选择资源领域；记忆编辑器也可关联领域。Wiki/文档页上方的领域筛选器用于筛选资源；已删除领域会从筛选条件移除并提示。领域标签是资源分类，不是访问授权。证据：`src/web/workspace.tsx`、`src/modules/domains/ui/domain-tag-editor.tsx`、`src/modules/memory/ui/memory-library.tsx`、`src/modules/service-api/application/workspace-authorization.ts`。

### 记忆库

网页端记忆列表走摘要接口，只取 id、title、status、version、updatedAt、owner、category 这 7 个字段，点开某条才拉正文；摘要模式下列表不显示冲突块，这是已知限制，不是 bug。

- 打开“记忆库”，选择条目读取详情；共享网页先取摘要，选中后才加载全文。摘要搜索匹配标题/分类，不是全文搜索；全文模式另匹配正文。需要 `memory.read`，编辑需要 `memory.write` 且在该条目的可写范围内。证据：`src/web/workspace.tsx`、`src/modules/memory/ui/memory-library.tsx`。
- 分类采用七类软词表：`identity` 身份、`preference` 偏好、`fact` 事实、`decision` 决策、`procedure` 流程、`context` 上下文、`reflection` 反思。未知分类归一到 `context`；这是当前临时词表，不能自行假定任意分类都会原样保存。证据：`src/modules/memory/domain/category.ts`。
- 重要度 `importance` 与可信度 `credibility` 是两个独立的 0–1 指标，`null` 表示未知。界面展示二者，不能把未知解释为零或把重要度当成事实可信程度。证据：`src/modules/memory/domain/model.ts`、`src/modules/memory/ui/memory-library.tsx`。
- 状态徽标：`candidate` 待提升、`active` 当前有效、`superseded` 已由其他记忆替代、`expired` 已过期、`archived` 已归档。普通写入不能直接指定状态；治理操作见第 2 节。过期读取过滤不等于已持久化状态迁移，非 active 内容还受额外可见性限制。证据：`src/modules/memory/domain/lifecycle.ts`、`src/modules/service-api/application/workspace-authorization.ts`。
- 详情含版本与修订历史；若修订已压缩，显示压缩提示并仅列保留区间。当前没有在该界面浏览所有归档修订的完整历史入口，不能把所列历史当成全部底层记录。证据：`src/modules/memory/ui/memory-library.tsx`、`src/modules/memory/domain/compaction.ts`。
- 详情展示 project / role / private 可见性；“私有”不是管理员天然可看，角色可见也取决于当前选中的工作角色。授权规则见第 2 节。证据：`src/modules/service-api/application/workspace-authorization.ts`。
- **摘要列表模式下不显示冲突块**：组件明确将 `conflicts` 置为空；摘要没有用于完整冲突检测的正文集合，加载单条详情也不会切换到全量检测。仅在传入完整 memories 的模式下，才检测并显示涉及当前条目的冲突。看不到冲突块不等于没有冲突。证据：`src/modules/memory/ui/memory-library.tsx` 的 `summaryMode` / `detectConflicts`。

### 星图

桌面星图组件可将 Wiki 或记忆绘成点线场景，并按领域/搜索条件过滤、选择节点；点线数量存在上限。共享 Web 的项目页签当前只有 Wiki、文档、记忆库、知识领域，没有星图页签，不能从那里寻找星图按钮。证据：`src/components/workspace/memory-star-map.tsx`、`src/modules/star-map/application/workspace-scene.ts`、`src/web/workspace.tsx`。

颜色是分组结果，不是可信度等级：记忆优先按分类分组，否则取排序后的第一个领域名，再否则未分类；`seaColor(group)` 将分组哈希映射到调色板。Wiki 按节点 type 取色。基础 weight 对记忆为 `1 + min(4, relatedIds.length * 0.3)`，Wiki 为 `1 + min(4, sqrt(linkCount) * 0.3)`，投影还会影响屏幕大小。证据：`src/modules/star-map/domain/scene.ts`、`src/modules/star-map/application/workspace-scene.ts`。

星体映射按以下优先级命中即停（证据：`src/modules/star-map/README.md`、`src/modules/star-map/domain/bodies.ts`）：

| 条件 | 星体 / 外观 |
| --- | --- |
| archived / superseded / expired | remnant，暗淡虚线历史星体 |
| validity.until ≤ 当前时间 + 30 天（包含已过期） | comet，带尾迹 |
| importance 非空且 ≥ 0.7 | star，星芒 |
| relationCount ≥ 3 | nebula，云状 |
| relationCount ≥ 1 | moon，月牙 |
| 其余 | planet，圆盘 |

记忆的体积倍率为 `importance === null ? 1 : 0.8 + importance * 1.6`，亮度为 `credibility === null ? 0.6 : 0.35 + credibility * 0.65`。规则读取的是 relations 数量，基础 weight 使用 relatedIds 数量，两者不要混为一谈。Canvas 支持减少动态效果设置；这些渲染规则不证明共享服务已经提供授权图查询。

## 2. 管理员（admin）

### 账号、角色与当前身份

首次初始化走 `POST /api/v1/auth/bootstrap`，需服务端配置的初始化 key，经 `X-KW-Setup-Key` 校验后建立首个账号；之后用 `POST /api/v1/auth/login` 登录。不要把初始化 key 当成日常登录密码。身份与授权管理中的“账号管理”支持创建 user / agent / admin、停用/恢复账号；Agent 使用 Token，创建后还需要加入项目。证据：`server/auth-http.ts`、`src/modules/identity/ui/identity-console.tsx`。

“项目成员”授予 viewer / editor / manager 和工作角色；“工作角色”配置明确的权限子集，再授给成员。切换工作角色会重算有效权限与可见内容，不是只改显示名称；授权不能突破成员权限上限，Token、委托还会进一步约束范围。界面按 `wiki.read`、`documents.read`、`memory.read`、`project.read` 显示页签，按 `wiki.write`、`memory.write`、`domains.manage` 控制写入。证据：`src/modules/identity/domain/policy.ts`、`src/modules/identity/application/access-context.ts`、`src/web/workspace.tsx`。

### 私有、角色和 grant

- project 记忆仍需基础 `memory.read` / `memory.write`；role 记忆要求当前 `workRoleId` 命中记忆的 `workRoleIds`。
- private 记忆由真实所有者本人访问（actor 与 effectiveAccount 一致），或由给真实 actor 的有效 grant 授权；身份委托不自动继承私有记忆。
- `GET/POST /api/v1/projects/{projectId}/memories/{memoryId}/grants` 查看/新增授权，`DELETE` 其 `/{grantId}` 撤销。只有实际所有者可管理；明确被授权 `accountId`、`actions: ["read", "write"]` 的所需子集、未来的 `expiresAt`。grant 还要匹配项目、记忆和所有者，未撤销且未到期，并且不替代基础权限。
- 非 active 记忆读取先限定为真实本人且为来源作者或所有者；到期内容会被读取过滤。不能承诺持有 grant 就能读全部历史状态。修改可见性也受所有者约束。

以上证据：`server/auth-http.ts`、`src/modules/identity/domain/memory-grant.ts`、`src/modules/service-api/application/workspace-authorization.ts`。

### 提案与批准

Agent 的受控写入流程必须先提交提案，落为 `pending`；批准成功才应用到 Wiki/记忆。提交 `POST /proposals`，查看 `GET /proposals`，人工决策 `POST /proposals/{id}/approve` 或 `/reject`（拒绝需 reason）。提交/决策路由要求 `wiki.write`，列表要求 `wiki.read`；应用记忆还会经过 `memory.write` 的仓储检查。证据：`server/http.ts`、`src/modules/service-api/application/service.ts`、`src/modules/service-api/application/authorized-repository.ts`。

`POST /proposals/approve-batch` 支持 ids / kind 筛选；按规则入口记录 `via: rule`，当前规则就是选择 pending 且符合筛选条件的提案，不是自然语言自动审批引擎。`dryRun: true` 只返回 eligible，不实际批准；eligible 不保证正式应用时无版本/权限错误。正式结果分别看 approved / failed，不能将一次批量请求理解为全部成功。证据：`src/modules/service-api/application/service.ts` 的 `approveProposals`。

**当前没有可据此宣称的全入口强制审批隔离**：核对的共享 HTTP 直接 Wiki/记忆写入及批准方法未见统一的“Agent 禁止直写/禁止自批”角色拦截。pending 是提案流程的真实行为，不能扩大为所有写入口都已强制执行。使用时只给 Agent 所需范围并走提案流程；本手册不将此缺口写成已完成能力。证据：`server/http.ts`、`src/modules/service-api/application/service.ts`、`server/resource-tools.ts`。共享网页当前也没有提案审批页签，以上以 HTTP 接入面使用。

### 记忆治理

以下是项目下 `POST /memories/{id}/{operation}`，要求 `memory.write`，不是 admin 账号名称本身赋予权限。证据：`server/http.ts`、`src/modules/service-api/application/service.ts`、`src/modules/memory/application/service.ts`。

| operation | 效果与前提 |
| --- | --- |
| promote | candidate → active，非 candidate 会冲突 |
| archive | 转为 archived，保留记录，影响后续可见性/召回 |
| supersede | 两条必须为不同的 active 记忆；旧条变 superseded，并建立替代关联 |
| resolve | 两条必须 active；记录 a-canonical / both-intentional / merged 决策与可选 note；不是自动合并正文，也不自动替代状态 |

记忆库组件提供提升、归档和替代操作；摘要模式没有冲突块。治理仓储入口当前只检查 `memory.write`，不能承诺它已实现与普通逐条读写完全相同的可见性校验；不要把它描述为可安全授予任意外部 Agent 的入口。证据：`src/modules/memory/ui/memory-library.tsx`、`src/modules/service-api/application/authorized-repository.ts` 的 governance 方法。

## 3. 外部 Agent / CLI

### 三种实际接入面

1. `mcp-server/` 是桌面 MCP：要求桌面运行，在“设置 → API + MCP”启用本地 HTTP API 与 MCP；默认 `http://127.0.0.1:19828/api/v1`。环境变量 `LLM_WIKI_API_TOKEN` / `LLM_WIKI_API_BASE_URL`；工具包括 status、projects、set_project、files、read_file、reviews、search、chat、graph、rescan_sources。遵循桌面 Token/路径白名单，不能套用共享服务的权限名；chat、set_project、rescan_sources 不能统称只读。证据：`mcp-server/README.md`、`mcp-server/src/api-client.ts`。
2. `npm run kw:cli -- <projectId> <operation>` 调用已构建的 `dist-service/cli.mjs`，stdin 接收 JSON 对象。`KW_API_URL` 默认 `http://127.0.0.1:4317`，`KW_AGENT_TOKEN` 放进进程环境，选填 `KW_ACCESS_CONTEXT`；不把 Token 放命令参数。支持 `context.switch`、`wiki.list/read/write`、`documents.list`、`memory.list`、`search`，不是任意 shell 命令执行器。证据：`package.json`、`server/cli-main.ts`、`src/modules/cli/application/remote.ts`。
3. 共享服务 HTTP：Bearer Agent Token 或账号会话，选用 `X-KW-Context` 绑定上下文。下表所有相对路径均以 `/api/v1/projects/{projectId}` 为前缀；“只读”指不修改业务资源，查询可能仍有审计记录。证据：`server/http.ts`、`server/auth-http.ts`、`src/modules/service-api/application/authorized-repository.ts`。

| 方法 / 路由 | 所需权限及范围 | 只读 |
| --- | --- | --- |
| GET /memories | memory.read；底层 workspace 读取还需 project.read，按可见范围过滤 | 是 |
| GET /memories/summaries?limit&cursor | memory.read；limit 为整数 1..200，默认 50；cursor 为 `<updatedAt>\|<id>`，返回 `{ items, nextCursor }`，末页 nextCursor 为 null | 是 |
| GET /memories/graph?limit | memory.read；limit 为整数 1..2000，默认 500；返回 `{ items }`，节点不含正文 | 是 |
| GET /memories/{id} | memory.read；底层 workspace 的 project.read 与逐条可见性 | 是 |
| POST /memories/search | memory.read；workspace 的 project.read，只返回可见 active 命中 | 是 |
| POST /memories/recall | memory.read；workspace 的 project.read，按上下文和字符预算召回 | 是 |
| POST /memories | memory.write；更新另受资源授权检查 | 否 |
| POST /memories/{id}/promote、archive、supersede、resolve | memory.write；治理限制见第 2 节 | 否 |
| POST /memories/expire | memory.write；持久化到期迁移 | 否 |
| GET /proposals | wiki.read | 是 |
| POST /proposals | wiki.write；创建 pending | 否 |
| POST /proposals/{id}/approve、reject | wiki.write；记忆应用还需 memory.write | 否 |
| POST /proposals/approve-batch | wiki.write；记忆应用还需 memory.write；dryRun 不应用 | 仅 dryRun 是 |
| GET /workspace、GET /workspace?memories=none | project.read（并非 memory.read）；不适用 limit；memories 参数只接受 none，默认不裁剪；返回 workspace 资源对象（含 data、revision），none 仅将 data.memories 置为 []，其余数据及 revision/ETag 不变 | 是 |
| PUT /workspace | memory.write 或 domains.manage；变更领域必须 domains.manage，记忆变更需可写范围 | 否 |
| GET /wiki、/wiki/page?path=wiki/... | wiki.read | 是 |
| PUT、DELETE /wiki/page?path=wiki/... | wiki.write；带版本前置条件 | 否 |
| POST /search、/retrieval | wiki.read；当前此入口为 keywordSearch | 是 |
| GET /documents、/documents/{id}/ingestion、/documents/{id}/receipt | documents.read | 是 |
| POST /documents | documents.write；仅接收原始文件 | 否 |
| POST /mcp、/cli（tool 请求） | wiki.list/read/search: wiki.read；wiki.write: wiki.write；documents.list: documents.read；memory.list: memory.read，并受 workspace 授权约束 | 除 wiki.write 外是 |

本次核对 `server/http.ts` 已有 `/memories/graph` 专用只读路由，契约见上表；接口存在不代表共享网页已有星图页签。

### 写入契约

上述新增查询契约核对来源：`server/http.ts` 的 summaries、graph、workspace GET 分支；`src/modules/service-api/application/service.ts` 的 readMemorySummaries、readMemoryGraph、readWorkspace；workspace 的 project.read 另见 `src/modules/service-api/application/authorized-repository.ts` 的 get。摘要与关系图均返回对象包裹的 items，不是直接数组。

直接记忆写入 `POST /memories` 的 body 为 `{ memoryId, input, expectedVersion, idempotencyKey? }`。`input` 白名单只有 `title/content/category/domainIds/relatedIds/access/importance/credibility/validity`；带 `status` 等其他键返回 400。创建用 `expectedVersion: null`，修改用读到的版本；409 的 `error.details.currentVersion` 可用于重新读取后人工重试。幂等键同项目、同内容重放返回 replayed，不同内容复用同键会冲突。Wiki 的 If-Match 是资源 revision，不是记忆条目 version。证据：`server/http.ts`、`src/modules/service-api/application/service.ts`、`src/modules/memory/application/service.ts`。

提案另用自身的 idempotencyKey，重复同指纹返回原提案，键相同但内容不同返回冲突；目标写入仍做版本检查。Agent 应提交 pending 提案等待有权限的人批准；不能用 input.status 绕过状态治理，也不能把“提案已接收”当成已生效。证据：`src/modules/service-api/application/service.ts`。

**没做的能力**：跨进程任务队列当前没有完成；外部 CLI 的完整适配契约 I01 未完成（`TASKS.md` 的 I01 仍未勾选）。仓库有本地 transport、共享 CLI 和任务队列代码，并不证明完整外部适配、跨进程调度或本机真实 CLI 验收完成。证据：`src/modules/cli/README.md`、`src/modules/tasks/README.md`、`TASKS.md`。

| proposal.submit | 写 pending 提案 | wiki.write | C |
| proposal.list | 读 | wiki.read | C |
| context.switch | 写上下文选择 | 已认证主体；校验身份选择与项目范围 | POST /api/v1/projects/:id/contexts |

共享 CLI / MCP 的记忆写入必须走提案：`proposal.submit` 只创建 pending 提案，批准前 `memory.summaries` 看不到；批准仍只能在 Web/管理员侧做，共享工具没有批准操作（不代表所有底层入口已强制隔离 Agent）。幂等键同键同内容返回同一条提案，同键换内容返回 **409**。

带 cookie 的写请求必须带 `X-KW-CSRF: 1`；Agent Token 请求不需要该头，也不该带 cookie。全链证据：`analysis/release/evidence/2026-11-11-shared-cli-smoke.md`。

## 4. Obsidian / 本地文件

本地 Wiki 的 `.md` 文件是内容唯一真相源，索引是可重建派生物；此表述不意味着共享服务数据库会自动和任意 Vault 双向同步。索引一致性适配器读取 `wiki` 文件及 SHA256，启动时检查派生索引，缺失、损坏或文件版本变化时标为 stale 并排队；查询需通过一致性检查。不是保存任意 `.md` 后立刻保证已完成 embedding。证据：`src/app/retrieval/index-consistency.ts`、`src/lib/index-consistency.ts`。

变更后索引过期、派生数据缺失/损坏、或删除页面后存在孤立向量时，需要重建；`src/lib/rebuild-index.ts` 提供 startup + rebuild 入口。重建完成依据索引证据与检索结果，不能只看文件存在或 Source Watch 扫描成功。具体重建命令和运维操作引用 `runbook-20261110.md`。

共享网页“文档”页下方的“本机 Obsidian Vault”面板用于把当前授权项目的**处理回执**同步到本机选定 Vault，原笔记保持不变。先按面板引用的 `analysis/implementation/d08-local-vault-connector-contract.md` 在本机配置连接器，再填一次性配对码，点“配对”与逐文档“同步回执”；可“撤销连接”，连接有到期时间。凭据只放本机，不能填网页。证据：`server/vault-connector.ts`、`src/web/vault-connector-panel.tsx`。

连接器固定 loopback，默认端口 4319；若 HTTPS 网页被浏览器阻止连接，本机设置 `KW_DOCUMENT_ID` 后运行 `node dist-service/vault-connector.mjs --pull` 可拉取回执。它当前没有任意 Vault 笔记上传、双向同步或用浏览器直接监听本地文件的能力；不要把“已同步回执”读成“所有笔记已入库”。证据：同上两文件与 `src/web/workspace.tsx` 页脚。

## 5. 一页速查表

下表是默认项目权限上限；工作角色、Token、委托和逐条访问范围可进一步收窄。admin 是账号类型，不等于无条件拥有所有私有正文。证据：`src/modules/identity/domain/policy.ts`、`src/modules/service-api/application/workspace-authorization.ts`。

| 操作 | 权限 | 默认 viewer / editor / manager |
| --- | --- | --- |
| 进入项目、读 workspace | project.read | 三者可；内容继续过滤 |
| 读 / 写 Wiki | wiki.read / wiki.write | 三者读；editor、manager 写 |
| 读 / 上传文档 | documents.read / documents.write | 三者读；editor、manager 上传 |
| 读 / 写记忆 | memory.read / memory.write | 三者读；editor、manager 写；私有/角色额外限制 |
| 管理领域 | domains.manage | editor、manager |
| 提交 / 批准提案 | wiki.write；记忆应用另需 memory.write | editor、manager 的有效授权范围；不等于已强制禁止 Agent 自批 |
| 记忆 promote / archive / supersede / resolve | memory.write | editor、manager；治理校验局限见第 2 节 |
| 管成员 / 工作角色 | members.manage / roles.manage | manager |
| 确认共享工具是否存在 | 查注册表与漂移测试 | `analysis/architecture/shared-api-surface.json`、`server/api-surface.test.ts` |

遇到症状先看：

1. 保存 409：复制草稿，核对 Wiki revision / 记忆 currentVersion，再读最新版；见第 1、3 节。
2. 看不到条目/按钮或收到 403：核对当前项目、工作角色、Token/委托有效期、私有 grant；见第 2 节。
3. 上传成功却不能检索、或 Vault 显示已同步：先区分收件、处理回执和索引证据；见第 1、4 节及运维 runbook。

交付自检：四类受众均对应现存组件/命令/路由；明确保留的缺口包括自动冲突合并、共享网页星图/完整阶段台/审批页、摘要冲突检测、完整归档历史浏览、全入口强制 Agent 审批隔离、跨进程队列、I01 完整外部 CLI 适配、任意 Vault 双向同步。未将记忆图查询、收件、回执同步或索引派生物冒充已入库/已完成能力。
