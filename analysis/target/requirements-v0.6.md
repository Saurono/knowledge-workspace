## 2. 界面信息架构

### 2.1 应用整体

- user/admin 登录入口 → 选择知识库 → 主工作区；agent 通过 API Token 进入服务 API。本地客户端和 Web 客户端保持主要业务概念一致。
- 左侧导航取消“搜索”和独立“检查”入口；原有其他入口的保留与调整，未被本次要求取消。
- 新增“任务管理器”入口。其内部顶栏提供三类任务标签；不擅自将应用全部页面改为顶栏标签。
- 新增“记忆库”入口；原“关系图”入口更新为“记忆星图”，顶部按钮切换 Wiki/智能体记忆两类图数据。
- 知识领域为扁平标签。建议在内容导航中显示可多选的领域筛选，并在对话/Wiki/资料中复用分类范围，不增加父子领域树。

### 2.2 对话页

```text
对话                         [ 本地搜索 | LLM 对话检索 ]
知识库 / 知识领域范围
------------------------------------------------------
本地搜索：输入 → 本地知识内容结果 → 打开文档或 Wiki
LLM 对话检索：输入 → 收集证据 → 生成回答 → 引用预览
------------------------------------------------------
输入框
```

“本地搜索”暂按直接返回已入库内容的检索结果理解，不调用生成模型来回答；是否使用已有向量索引、是否检索原始资料以及是否允许远程 Embedding，需明确后再落实现。它与“本地部署模型”不是同一概念。

现有 Agent 模式 fast/standard/deep/local_first 与检索模式 standard/smart/faithful 属于底层不同配置；不能把新按钮直接绑定到原有 local_first。建议在 LLM 模式内再决定哪些高级设置对用户可见。

切换时建议保留各模式输入与结果，避免将直接搜索结果误存成 LLM 回答。两种模式使用相同的领域范围和权限过滤。

### 2.3 Wiki 页

```text
Wiki       当前页面          [ 编辑模式 | 预览模式 ]
领域分类 / 来源 / 页面元数据           [ 检查与纠错 ]
------------------------------------------------------
知识树 | 正文编辑器或只读预览 | 检查问题与修复建议
------------------------------------------------------
当前选中内容有任务运行时：处理中
```

- 编辑/预览是正文呈现方式；检查与纠错是 Wiki 内的操作区，两者分开定义，避免用一个切换器混淆三种状态。
- 预览模式不允许直接改正文。修复动作若会改文档，应保留明确的执行交互和结果。
- Wiki 显示检查发现的内容问题、修复建议和可用动作；任务运行详情统一放任务管理器。
- 保留结构检查、语义检查、规则忽略项、进度取消能力、断链修复、补链接/占位页、孤立页处理、批量修复、送审/忽略等原 Lint 页功能；其中进度与取消入口迁移到任务管理器。
- 现有 Review 是独立人工判断业务，本次未要求把 Review 全页并入 Wiki；“送审”仍可联动它。

### 2.4 任务管理器

```text
任务管理器
[ 文档导入任务 ] [ 深度研究任务 ] [ Wiki 检查与纠错任务 ]
------------------------------------------------------
筛选范围 / 状态
任务列表                         选中任务详情
任务名称、对象、状态、时间        阶段 / 进度 / 日志
                                错误 / 结果 / 重试等操作
```

- 三类任务的详细状态、进度、日志和操作只在此统一展示。
- 业务页保留“提交导入 / 发起研究 / 运行检查 / 执行纠错”等触发能力和结果内容；移除任务列表、运行日志、进度条及重复的任务操作区。
- 文档导入任务覆盖复制/抓取、解析、知识编译、衍生索引等阶段，阶段与一个任务的聚合关系需要在实现时统一。
- 研究任务完成后触发知识编译时，以父子任务/关联关系连接文档导入任务，避免重复汇报成功或把研究完成误认为入库完成。
- 检查与纠错统一为一个任务分类；检查产生“发现”，纠错产生“修改”，不能将二者合并为同一个成功条件。
- 支持的暂停/取消/重试能力按执行器实际支持显示；不为所有任务展示没有实现的按钮。

## 3. 两种前端的推荐技术边界（设计建议）

推荐共享业务 UI 与 API 协议，采用可复用后端服务承载身份、内容、检索、Agent 和后台任务。本地客户端保留 Tauri 容器与本机能力适配；Web 通过受控上传与 API 使用服务。

这是一项架构建议，尚未确定两端必须连接同一中心服务。本地独立部署、完全离线以及账号同步策略仍需决策。

| 能力 | 本地前端 | Web 前端 | 推荐共享层 |
|---|---|---|---|
| 领域、Wiki、对话、任务界面 | React 共享组件 | React 共享组件 | 领域对象与状态定义 |
| 账户与权限 | 登录会话适配 | 浏览器登录会话 | 身份和授权服务 |
| 文件导入 | 文件/文件夹选择与上传或本机接入 | 浏览器上传 | 资料生命周期与任务协议 |
| 目录监听、Shell、本机文件打开 | Tauri/本机适配 | 不直接提供任意本机访问 | 可选执行节点，明确作用范围 |
| Wiki 和任务持久化 | 本地服务或共享服务 | 服务端 | 内容/任务存储接口 |
| 检索与 LLM Agent | 统一协议 | 统一协议 | 检索/证据与模型路由 |
| 任务事件 | 订阅服务事件 | 订阅服务事件 | SSE/WebSocket + 状态查询 |

当前前端含 Ingest、Research、Lint、定时扫描等实际执行逻辑。为了让切页和关闭业务视图不影响任务，应先迁移执行责任到后端/执行器，再统一任务界面。Web 浏览器也不能直接复用 Tauri invoke 和任意磁盘路径。

## 4. 知识领域分类模型（已确认扁平、多选）

已确定新增扁平领域标签，一份内容可关联多个领域。建议采用独立领域对象，而非把领域名称直接等同于磁盘文件夹或 LLM 页面类型。

建议对象：Domain(id, knowledgeBaseId, name, description, order)，不设置 parentId。使用 DocumentDomain(documentId, domainId) 与 WikiPageDomain(pageId, domainId) 多对多关联；每个关联对保持唯一。领域是否跨知识库共享尚未确定，当前建模建议作用于知识库。

- 原生 page type（entity/concept/source/query 等）描述内容类型；知识领域描述业务归属，应允许并存。
- 分类筛选需进入检索和 LLM 证据范围；只在侧栏显示名称不能满足实际知识组织。
- 未分类内容应可见并可补分类。
- 分类删除、排序、重命名和导入时分配策略需要明确；自动分类为候选能力，尚不是用户已确认要求。
- 跨领域生成页面和共享来源不能仅依据存储目录推断归属。

## 5. 登录与三角色

| 角色 | 已确定 | 尚未确定 |
|---|---|---|
| user | 存在此角色 | 阅读/导入/编辑/研究/纠错等权限及知识库范围 |
| agent | 程序/AI Agent 专用身份，通过 API Token 访问，不作为人工交互登录角色 | Token 签发/撤销权限、有效期、可执行工具和读写范围 |
| admin | 存在此角色 | 是否管理全局用户、领域、模型、任务及知识库授权 |

建议服务端执行所有授权校验，并将 UI 可见性作为展示行为。账户角色、知识库访问范围、领域分类是三个不同维度；不能仅通过隐藏导航实现权限。

agent 的 Token 应绑定一个明确的 agent 身份；建议支持撤销、轮换与范围约束，不能将旧的全局 API Token 直接等同于某个账户。user/admin 的登录凭证形式和具体权限尚未确定。

任务应记录创建者与执行身份，以便后续展示“谁发起、谁执行”。Agent 的任务和写页权限应使用与用户请求一致的授权入口。

## 6. 统一任务契约（设计建议）

建议最小字段：id、knowledgeBaseId、category、action、createdBy、executionIdentity、targetRefs、parentTaskId、status、stage、progress、resultRefs、error、createdAt、updatedAt。

- category 固定首批三类：document_import、deep_research、wiki_maintenance。
- action 区分 ingest/parse/check/fix 等执行行为，避免把分类写死为一种实现。
- 建议公共状态 queued/running/succeeded/failed/cancelled；暂停、等待输入/授权作为可选状态，不要求每种执行器都支持。
- 持久化状态与执行进程生命周期分离；任务页切标签不触发取消或重新执行。
- 重连先取状态快照，再续订事件；重试保留尝试记录，避免重复写页。
- 当前选中文档/Wiki/任务的“处理中”标记由任务关联关系推导，状态终止后清除，不另建一套可能失步的前端布尔值。

## 8. 尚待确定的语义

1. user/admin 的登录方式、三类角色的具体权限，以及 agent Token 管理规则。
2. 领域标签是否跨知识库共享；多标签筛选是满足任一标签还是全部标签，建议可显式选择。
3. “本地”前端的部署方式：本地独立服务还是连接中心服务；离线是否是首版要求。
4. “本地搜索”是否覆盖来源原文、向量检索；是否要求不触发任何远程调用。
5. “只在选中进行的任务做处理中的标记”的承载位置：业务页当前内容，还是任务管理器中的当前选中任务。

以上未定项不阻塞需求拆解与源码映射；依赖它们的权限、数据关系和运行方式不作为已拍板设计。

## 9. 首版验收场景

- 本地、Web 可通过各自入口进入对应知识库，核心业务数据和权限行为符合所选部署方案。
- user/admin 能登录；agent 使用绑定身份的 API Token 访问；三角色均可识别，未授权操作由后端拒绝；具体动作依据后续权限矩阵验收。
- 新建扁平领域标签，将同一文档/Wiki 同时归入多个领域；筛选 Wiki、资料和检索证据，未分类内容不会丢失。
- 左栏不再有搜索/检查入口；对话两模式可以切换；直接搜索与 LLM 回答的结果呈现清晰。
- Wiki 可切编辑与预览；原检查功能逐项可达，检查结果/纠错动作在 Wiki，运行进度/日志在任务管理器。
- 顶部三类任务标签可分别查看对应任务；跨页或切标签不影响执行；失败可定位、可按支持能力重试/取消。
- 业务页不出现旧活动面板、研究进度侧栏等重复任务 UI；“处理中”标记只按最终确认的选中范围显示并随终止状态清除。
- 研究报告生成与后续入库关联清晰；纠错写入有结果记录；重试不造成重复入库或覆盖错误版本。
