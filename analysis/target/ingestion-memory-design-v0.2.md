## 2. 源码现状与改造切入点

- 原生通过创建 `.obsidian/` 配置以及 Markdown/Wiki 链接提供兼容；未发现完整的“Obsidian 导入状态回传”产品链路。依据 `src-tauri/src/commands/project.rs`。

- 增量缓存计算内容 SHA256。本方案不写回源笔记；独立回执目录仍须排除在所有导入/监听入口之外，避免回执自身被重复入库。依据 `src/lib/ingest-cache.ts`。

- 现有会话持久化和 Agent session 不等于可治理、可检索的长期记忆库。本次静态检索未发现独立记忆页与完整长期记忆 CRUD 链路。

## 3. 推荐入库流程

```text
选资料/接收 Obsidian 笔记
 → 接收校验：身份、目标知识库、领域标签、格式与大小
 → 登记来源、内容版本和持久任务，立即返回 taskId
 → 判断内容是否变化：相同版本复用已有有效结果
 → 资料快照与解析：文字、结构、图片及来源定位
 → 知识编译：分析 → 页面生成/合并
 → 持久写入与来源映射
 → 检索索引更新
 → 生成入库结果清单
 → 独立执行 Obsidian 回传
```

### 3.1 成功边界

| 对外状态 | 含义 |
|---|---|
| 已接收/排队 | 已取得任务身份，不等于 Wiki 已生成 |
| 等待配置/输入 | 模型、连接或输入未就绪；原因可查，不静默当成成功 |
| 解析中 | 正在提取资料，失败可定位具体文件 |
| 知识编译中 | 分析、生成、合并及写入阶段 |
| 内容已入库 | Wiki 与来源映射已持久化 |
| 检索准备中 | 正在建立已启用的检索索引 |
| 入库就绪 | 配置要求的知识资产与索引已就绪 |
| 失败/取消 | 明确失败阶段或取消结果，不发布虚假的“就绪” |

这些为任务 stage/结果状态语义建议，沿用统一任务契约，不建立第二套业务页任务列表。大批量导入采用批次父任务与文件子任务，允许显示部分成功与逐文件重试。

向量检索关闭时不等待向量索引；已开启但失败时显示“内容已入库、向量索引失败/待重试”，不要重跑整个 LLM 编译。接收、解析、编译和索引的重试边界分别定义。

### 3.2 来源与增量策略

- 建议登记 connectionId、sourceId、sourceRevision/contentHash、源笔记路径与目标知识库；路径变化更新映射，不能直接把重命名当成全新资料。
- 内容相同、来源不同的资料保留各自来源记录；复用处理结果不应抹去来源或越过不同账户的访问范围。
- 文件修改产生新版本。旧任务的迟到结果不能覆盖新版本的状态或产物映射。
- 外部源文件删除后的本地保留/归档/级联清理策略待确定；不把整个 Vault 当成应用可任意写删的托管目录。
- 域标签与原生知识类型并行保存；导入时可分配多个扁平领域，生成页面的领域继承规则需明确。

## 4. Obsidian 连接与回传

### 4.1 双前端下的连接边界

桌面端可通过本地连接器访问授权 Vault。Web 无法直接读写任意本机 Vault，推荐通过 Obsidian 插件或本地桥接器主动连接服务；也可采用导入/导出文件，但这不等于实时回传。

已确认回传载体：Vault 中的独立入库记录，不修改原笔记。推荐以 JSON 为规范记录，供外部软件读取；可选生成 Markdown 阅读视图，但它不成为第二套事实来源。连接器/Obsidian 插件仅负责投递或读取记录，采用哪种连接器仍待实现设计。Obsidian URI 可用于打开笔记，不应充当状态回传或身份验证机制。

连接凭证应绑定连接器身份及限定知识库范围，可沿用 agent 身份与 API Token 授权模型；凭证不写进笔记或回执内容。

### 4.2 建议回传信息

| 字段 | 用途 |
|---|---|
| receiptId / eventVersion | 回执去重与顺序判断 |
| connectionId / sourceId / sourceRevision | 确保回到正确 Vault、笔记和内容版本 |
| taskId / batchId | 与统一任务管理器定位到同一任务 |
| status / stage / updatedAt | 当前入库状态、阶段和时间 |
| sourceLink / wikiLinks | 原笔记回链和知识库产物链接 |
| indexed / indexStatus | 区分内容落盘与检索就绪 |
| resultSummary / errorCode | 简短结果或可行动错误，不回传完整内部日志 |

独立记录建议使用 `schemaVersion`、稳定 ID 和 ISO 8601 时间，外部软件不必解析自然语言日志。阶段事件可节流合并，终态回执必须持久可重试。字段协议草案见 receipt-example-v0.2.json。

### 4.3 回传可靠性

- 入库和回传分别记录状态：例如“入库就绪，Obsidian 回传待重试”。回传失败不触发重新解析和 LLM 调用。
- 建议采用持久 outbox、可重试投递和幂等应用。插件/桥接器离线后可从游标补拉，收到旧版本回执时不覆盖较新状态。
- 所有回传只更新独立记录目录，原笔记正文、frontmatter、链接和文件时间不因回传而修改。连接器写入权限限定到记录目录。
- 独立记录目录同时排除于手动文件夹导入、定时扫描和来源监听。建议先写临时文件，再原子替换正式 JSON，外部读者不读取半写入文件。
- 非 Markdown 附件通过独立记录关联，不尝试往 PDF/Office 二进制注入 Markdown 属性。
- 连接断开、改名、重试、应用重启及双端重复提交均需有对应策略。

Obsidian Vault 内的独立回执按用户要求向外部应用回传，不在本软件业务页复制一套进度面板。完整日志和操作仍在统一任务管理器；本软件业务页仅保留约定的选中对象“处理中”标记。

## 5. 记忆库功能页

### 5.1 页面建议

```text
记忆库              记忆范围 / Agent / 知识领域 / 类型筛选
--------------------------------------------------------
记忆列表                         记忆详情
摘要、类型、归属、更新时间        正文、来源、关系、版本
                                检索引用与可用管理动作
```

用户已确定独立记忆库功能页。以下建议能力需纳入后续产品评审：查询、查看、手动创建/编辑、归档/删除、去重、来源回溯、记忆之间以及记忆与 Wiki 的关系导航。

用户已有专门的记忆分类方案，稍后补充。当前保留分类 ID、元数据、来源及关系的扩展位置，不预定义事实/偏好/经验等类别；是否保存完整会话、如何提炼及何时写入由后续分类和生命周期要求决定。

### 5.2 建议数据模型与授权

Memory(id, knowledgeBaseId, ownerId/scope, agentId?, categoryId?, content, domainIds[], status, provenanceRefs[], createdAt, updatedAt, revision)。categoryId 的取值和专属字段等待用户分类方案，不能把知识领域标签直接当成记忆分类。

MemoryRelation(id, fromId, toId, relationType, provenanceRefs[], weight?)；目标可扩展为 Wiki/source 引用，但应保留目标类型与 ID 命名空间。

- Wiki 表达整理后的知识内容；记忆表达智能体为后续任务保留的信息。两者可相互引用，生命周期与写入策略分别治理。
- agent 使用现有确认的 API Token 身份访问记忆服务；查看、检索、写入、删除均由后端校验范围。
- 私有、共享、Agent 专属等范围是待选择的权限策略，不能默认所有 agent 共享所有用户记忆。
- 模型使用记忆时必须先过滤权限、状态与领域，再召回；记忆删除/归档同步更新检索索引和星图。
- 推断记忆与已证实事实应能区分。候选与生效状态、保留期、冲突处理、引用和版本策略待后续确定。

记忆提炼/批量整理若需要后台任务，不在记忆页添加独立队列；应纳入任务服务。是否新增第四个任务类别，或作为现有类别扩展，尚未获得用户指示，暂保留当前三标签要求。

## 6. 统一记忆星图

### 6.1 入口与模式

原“关系图”入口改为“记忆星图”，页面顶部固定切换：

```text
记忆星图     [ Wiki 关系 | 智能体记忆关系 ]
             领域 / 节点类型 / 搜索 / 范围筛选
--------------------------------------------------------
星图画布：节点、连线、聚簇、缩放与选择
选中节点详情：来源、关系解释、跳转 Wiki 或记忆详情
```

切换必须加载不同的数据集与关系语义，不只替换名称、颜色或在同一份 Wiki 图上加过滤器。建议分别保存两个模式的筛选、视角与选中节点；空态明确提示“暂无 Wiki 关系”或“暂无智能体记忆”，不混用节点。

### 6.2 星图风格建议

采用低干扰深色底、星点式节点、清晰的选中光环、细关系连线和可识别的星团布局；颜色说明领域/类型，大小和亮度的含义需在图例中明示。优先可读性与大图性能，动态效果可关闭，避免持续闪烁和装饰遮挡。

用户随后指定 asdfd3/3d-memory-sea 作为样式参考：当前采用 Canvas 三维透视星海，复用参考的旋转/平移/缩放方向。Wiki/记忆分别适配，原 Wiki 分析工具作为独立入口保留。详情见 graph-style-reference.md。

### 6.3 两类数据集

| 模式 | 节点 | 关系 | 详情跳转 |
|---|---|---|---|
| Wiki 关系 | Wiki 页面/实体/概念等 | 链接、来源共现与关联评分；需要区分显式链接和推断关联 | Wiki 页面与来源 |
| 智能体记忆关系 | 有权访问的生效记忆及获准关系节点 | 显式记忆关系、支持/冲突/替代/来源等；类型为建议，待定 | 记忆详情及证据 |

语义相似度不能直接显示为已确认事实关系。领域多选导致一条记忆归于多个领域时，仍是同一个节点，不在图中复制成多份记忆。跨数据集引用可在详情中跳转，首版不新增用户未要求的混合图模式。

## 7. 接口与执行器建议

- 入库接收 API 返回 taskId/sourceId/revision；任务查询/事件继续使用统一任务协议。
- 连接管理 API 负责 Vault 映射与授权；回执通道支持订阅或补拉，连接器确认后更新投递状态。
- 记忆 API 支持受权的查询/读取与管理；记忆写入记录 agent 身份和 provenance。
- 图数据接口显式携带 mode=wiki|agent_memory，并由服务端过滤权限及领域。
- 前端复用星图渲染容器，WikiGraphAdapter 与 MemoryGraphAdapter 分别供数；复用 UI 不意味着强行共用页面文件解析器。
- Obsidian 回传是文档任务的交付阶段/关联结果；不增加第四个任务标签，任务管理器可单独重试回传。

## 8. 验收场景

1. 接收资料后即可获得任务 ID；无模型配置、解析失败、部分批次失败均可在统一任务管理器定位。
2. 同版本重复提交不会重复生成；新版本不会被旧任务的迟到结果覆盖；来源重命名后仍回到正确笔记。
3. Vault 独立记录目录收到正确版本的状态和 Wiki 结果链接，外部软件能解析 JSON；离线后可补回执；回传失败可独立重试。
4. 回传前后原笔记内容哈希保持一致；独立 JSON/可选 Markdown 记录均不进入导入链路。非 Markdown 附件也有独立来源记录。
5. 两端均存在记忆库页；不同用户/agent 的记忆访问符合最终授权范围；删除/归档后召回和星图同步更新。
6. 星图两个切换模式的数据、类型图例和详情跳转正确；从 Wiki 切到记忆模式不会继续显示旧 Wiki 节点。
7. 星图领域多选不复制节点，推断关联有标识，大量节点下不丢失选中状态或造成持续动画干扰。
8. 导入、回传和记忆整理不在业务页重建分散任务面板；原有三个任务标签保持一致。

## 9. 待确认项

- Obsidian 插件或本地桥接器的连接方式；独立记录目录命名与外部读取协议版本。回传不修改源笔记已确定。
- 等待用户提供专门记忆分类方案，再定义记忆内容、分类字段、写入触发、完整会话保留和共享/私有范围。
- 多 Vault、Vault 与知识库是否多对多，以及外部删除传播策略。
- 本地搜索与 LLM 检索是否默认使用长期记忆；建议显式设置范围。
- 记忆后台任务将来如何归类；当前三类任务标签不擅自扩展。

## 10. 独立回执与 Wiki 时间标注（T18）

### 10.1 记录组织建议

建议目录：Vault 下 `kb-ingest-records/<connectionId>/<sourceId>/<sourceRevision>.json`。目录名可配置，必须被导入器排除。原笔记无需增加 ID 属性；连接器在自己的映射存储中维护笔记与 sourceId 的对应。

每个来源版本记录 taskId、状态、Wiki 结果列表、内容入库时间和回传时间。重试更新同一版本回执，使用 eventVersion 保证单调；历史版本分别保留。外部软件可按路径读取或使用后续索引协议，不依赖文件名中的中文标题推断身份。最新版本索引若提供，也应原子更新。

### 10.2 时间定义与展示

| 字段 | 定义 | 更新规则 |
|---|---|---|
| receivedAt | 文件被系统接收并登记的时间 | 区别于成功入库 |
| sourceIngestedAt | 该逻辑来源第一次成功完成知识内容入库的时间 | 原始入库时间，重试/索引重建不重置；完成事件时填写 |
| revisionIngestedAt | 此内容版本首次成功入库时间 | 新版本有新时间 |
| wikiCreatedAt | Wiki 页面首次实际持久创建时间 | 合并/重命名不重置 |
| wikiUpdatedAt | Wiki 内容最后成功变更时间 | 内容修改时更新 |
| recordedAt | 独立回执生成/更新时间 | 回传重试可更新，不冒充入库时间 |

Wiki 页面至少标注“Wiki 建立时间”和“原始文件入库时间”。多来源页面在来源列表中逐文件展示 sourceIngestedAt，不用一个时间覆盖多个来源。可补充最近内容变更时间，但不能替代用户要求的两个时间。

建议时间字段以 UTC ISO 8601 存储，界面按用户时区显示；现有 created/updated 日期字段做兼容映射，不能以当天日期伪造旧页面建立时间。历史来源时间无可靠记录时显示“未知/待补录”，不拿文件复制时间或 filesystem mtime 充当入库时间。

Wiki 元数据保存在知识库 Wiki 内容或规范页面元数据中，Vault 回执只是其可读取投影。当前 Wiki 创建发生在来源入库完成前时，也分别保留两个真实事件时间。

### 10.3 增补验收

- 回传任务仅修改专用记录目录；对原笔记正文/frontmatter 做前后内容比较验证一致。
- 外部程序能够按 schemaVersion 解析记录，识别来源、版本、任务状态及产物，不需要安装我们的桌面前端。
- 来源首次入库、后续更新、重试、回传重试和索引重建各自符合时间更新规则。
- 多来源 Wiki 显示每份原始文件入库时间；已有页面合并后 wikiCreatedAt 保持不变。
