# 跨 Agent 记忆系统与统一星图设计 v1

日期：2026-10-31（Asia/Shanghai）
状态：目标设计。现有代码仍为本地手动记忆与星海预览，尚未具备此文描述的服务端身份、并发和治理能力。

本方案借鉴通用的分层记忆、证据检索、摘要整理和遗忘机制，不是对 ChatGPT 内部实现、数据库或系统提示的复刻。已确认：默认按角色与项目共享，私有记忆需明确授权；可同时切换工作角色与获授权的权限身份。

## 1. 产品目标

1. 不同供应商、不同进程和不同设备的 Agent 可通过统一接口读取同一套获准共享的记忆。
2. 每个 Agent 有独立身份与可撤销凭证；可按授权切换角色；记录谁以哪个获授权身份、什么工作角色读写了哪个版本。
3. 记忆有类型、作用范围、来源、可信程度、有效期和整理规则；支持并发写入、冲突处理、更新、归档和删除。
4. 星图是记忆服务的一个授权投影；列表、搜索、Agent 召回和星图读取同一份规范记录。
5. 星体形态解释记忆分量与生命周期；内容分类、可信度、重要性是独立维度。
6. 本地/Web/所有功能页采用统一视觉系统，星图保持更丰富的空间表达。

## 2. 分层记忆：存什么、怎样被使用

| 层 | 内容 | 生命周期与写入 | 默认读取方式 |
|---|---|---|---|
| 核心规则 | 用户明确要求、项目约束、角色行为规范、不可违反的工作约定 | 管理者显式维护、版本化；Agent 可提出修改建议 | 当前范围内生效版本优先装入，注明来源和版本 |
| 工作记忆 | 当前任务目标、进行中的步骤、暂存判断、短期上下文 | 任务/会话作用域，有 TTL；不会自动全部进入长期库 | 当前任务优先；跨任务需显式晋升或授权 |
| 情景记忆 | 发生过的事件、执行记录、已做的决策及结果 | 追加为主，保留时间与来源；可被概括 | 按任务相似性、时间和范围检索 |
| 语义记忆 | 相对稳定的事实、术语、偏好、项目背景 | 有证据/归属；变化时产生新版本或替代关系 | 关键词/语义混合召回，检查有效性 |
| 程序记忆 | 已验证流程、方法、操作经验、工具使用约定 | 指明适用条件与验证结果；执行工具仍受服务端权限限制 | 与当前工作角色、任务匹配时调用 |
| 反思与综合 | 多次事件归纳出的经验、总结、跨主题结论 | 由整理任务提案，附支持与反例；审核后生效 | 按适用范围使用，保留原始证据入口 |

层级是组织与检索机制，不是默认权限等级。记忆的“业务分类”继续可扩展，用户后续分类可以挂在各层之下；领域标签仍为原有扁平、多选结构。

## 3. 身份、角色与共享

### 3.1 两套角色维度

- **权限身份**保持既有 user / agent / admin。user/admin 由人员登录；agent 为程序身份，使用绑定 Agent 的 API Token。
- **工作角色**用于任务视角，例如研究、编写、审阅、执行、记忆整理。它决定任务说明、允许访问的记忆视图与可执行动作模板；具体角色由管理者配置。
- 用户可同时选择工作角色和获授权使用的权限身份。使用带期限、范围和能力上限的 IdentityGrant 表达委托；服务端验证该操作者可使用哪个 effectivePrincipalId，而不是直接修改原账户类型。
- 稳定的 actorPrincipalId 记录真正操作者，effectivePrincipalId 记录本次被授予使用的身份；两者连同工作角色写入审计。原账户永久权限变更仍属于独立管理操作。

有效访问范围 = 身份委托授权（或本人授权）∩ 当前有效身份权限 ∩ 凭证能力上限 ∩ 工作角色授权 ∩ 记忆对象 ACL ∩ 当前项目/任务范围。任意一项拒绝即拒绝；不能由请求方自行声明有效身份来绕过校验。

### 3.2 可配置共享范围

支持个人、Agent 私有、工作角色、项目共享、知识库共享五类范围。已确认默认以项目与工作角色共同限定共享，私有记忆只有明确授予才可读写；所有共享都需明确作用域，不能靠“连在同一星团”决定访问权限。

私有内容的 ACL 必须明确覆盖真实操作者或明确的委托链；仅切到某个有效身份、或具备账号管理权限，不自动取得该身份的全部私有记忆。

同一条记忆可有多个获准角色与 Agent，不复制多份记录。敏感级别和共享范围分开建模：一个项目内仍可存在受限内容。

### 3.3 切换角色的完整流程

Agent 使用自己的 Token 建立会话 → 服务返回获准使用的身份与工作角色组合 → 选择 effectivePrincipalId/projectId/roleId → 校验 IdentityGrant、RoleGrant 和凭证上限 → 服务返回有期限的 contextId → 所有记忆操作携带 contextId → 切换时创建新上下文、重新授权并记录事件。

并发角色使用独立上下文；不修改进程级或账户级“当前角色”，避免同一 Agent 的两个并发任务互相覆盖角色。Token 的原始身份保持稳定。

界面提供组合选择“以谁的权限身份 / 以什么工作角色 / 在哪个项目工作”。切换时清空不再授权的列表、星图、检索缓存及工具会话，并为模型新建隔离上下文；不能把上一身份的私有对话直接拼入下一身份的提示。授权到期、撤销或范围变化后，后续请求重新校验。

### 3.4 初始权限建议（待细化）

| 能力 | 普通 Agent | 获授记忆整理能力的 Agent | 有权人员 / 管理员 |
|---|---|---|---|
| 读取/检索 | 当前上下文明确授权的范围 | 同样按范围限制 | 按自身授权范围 |
| 新增记忆 | 提交候选；附来源与归属 | 提交候选或按显式规则生效 | 可在授权范围手动确认 |
| 更新已生效记忆 | 产生修订提案，不直接覆盖 | 按规则合并，记录修订；核心规则仍需审核 | 按管理权限批准修订 |
| 改核心规则/共享 ACL | 提案 | 提案 | 具备相应权限时执行 |
| 处理冲突/删除 | 标记与提案 | 获准范围内处理 | 根据权限确认或执行 |
| 切换身份/角色 | 已被授予的身份与角色组合 | 同样按授权组合限制 | 可使用已获授权的组合；授予/撤销权限另需管理资格 |

管理员的账号管理权与任意私有内容读取权应分别授予，避免将两者默认绑定。

## 4. 规范记忆记录

Memory：id、knowledgeBaseId、projectId、layer、categoryId、title、content、domainIds、ownerPrincipalId、visibility、acl、status、importance、confidence、pinned、validFrom/validUntil、provenanceRefs、createdBy、updatedBy、createdAt、updatedAt、version。

附属记录：

- MemoryRevision：记忆 ID、版本、内容、作者身份、工作角色、修改原因、证据、时间。
- MemoryRelation：两端 ID、关系类型、来源、置信度、有效版本、创建者。
- MemoryProposal：新增/修订/合并/冲突/删除提案、差异、候选证据、处理状态。
- AgentPrincipal / Credential / IdentityGrant / RoleGrant / AccessContext：身份、凭证哈希、角色授予、会话范围。
- MemoryAccessEvent：动作、主体、工作角色、对象版本、结果、时间与请求 ID；不记录原始 Token。
- StarPlacement：记忆 ID、布局版本、坐标、手动调整、可视投影参数；位置不决定权限或事实。

版本和来源是必须字段。缺失来源的模型推断可以作为候选，但不能凭其重要性或被多次读取而成为高可信事实。

## 5. 规则与生命周期

### 5.1 基本规则

1. 所有读取、图谱查询、摘要和检索先执行服务端授权。搜索分数、数量和星团统计都不能泄露未授权对象。
2. 每条生效记忆应是可独立理解的信息单元，带作用范围与来源；长会话先按事件整理，不整段无差别升为长期事实。
3. user 明确给出的工作要求高于同范围 Agent 的推断总结；读取较低层记忆不能改变工具权限或系统执行边界。
4. 内容中的指令按其类型处理。外部资料和普通记忆文本是证据；只有获授权且生效的规则记录才进入规则装载流程。
5. “重要”和“可信”分开记录。低可信的重要候选需要优先核实，不是直接增强召回权重后反复使用。
6. Agent 的重复转述不算独立证据。来自同一源的副本追踪 lineage，避免多 Agent 相互引用造成虚假共识。
7. 没有证据的新结论先成为 candidate；正式规则/跨项目高影响变更按政策审核。政策可允许低风险类型自动生效。
8. 过期不等于错误，替代不等于删除。保留版本与 supersedes 关系，默认检索采用当前有效版本。
9. 读取次数不能直接触发“恒星晋升”；重要性提升有原因、范围和规则版本，可人工调整并审计。
10. 删除经授权执行，先撤回未来召回和星图展示，再异步清理派生索引/缓存；清理状态可跟踪。此前已发给 Agent 的文本无法通过删除记录自动回收。

### 5.2 状态流转

candidate → active → superseded / expired / archived；conflicted 表示存在未解决争议，需明确提示或暂缓作为确定结论使用。rejected 与 deleted 退出普通召回。

单条内容可以有某个字段已确认、另一个字段待核实；首版优先拆成原子记忆，避免复杂字段级权限/状态。

### 5.3 并发与冲突

- 创建请求携带 idempotencyKey，重试不重复创建。
- 修订请求携带 expectedVersion 或 If-Match；不匹配返回 409 和差异，Agent 重新读取、合并或提交提案，不使用最后写入者无条件覆盖。
- 可自动合并去重后的领域标签等无冲突元数据；正文含不同事实时显式建争议，不让 LLM 静默选边。
- 合并在事务中完成：规范记忆、版本、关系、审计、outbox 同时提交。向量索引和星图消费同一事件序列，支持重放与重建。
- 服务端数据库提供并发一致性；浏览器锁、文件写锁和共享 workspace.json 不能承担跨进程/设备的写入仲裁。

## 6. Agent 如何读、如何写

### 6.1 读取管线

身份/角色上下文 → 权限和有效期过滤 → 当前任务工作记忆 + 生效核心规则 → 关键词/向量召回 → 显式关系扩展 → 去重/版本筛选 → 按相关性、来源质量、适用性和时效排序 → Token 预算装箱 → 返回内容、证据、版本、适用条件及冲突提示。

服务返回供应商无关的 MemoryContextPack：contextId、policyVersion、coreRules、workingState、relevantMemories、conflicts、evidence、readSet 和 budgetUsage，便于不同 Agent/API/MCP 客户端共用。核心规则装载不足时明确返回预算问题，不静默丢弃强制约束。

服务返回 readSet（本轮读到的 ID/版本），用于回答引用和后续更新。召回排序的权重应通过实际任务评估确定，不宣称某个未经评估的公式就是模型的记忆机制。

### 6.2 写入管线

任务产生信息 → 提取候选 → 同范围查重与冲突检测 → Agent 提案（来源、原因、预期有效期）→ 按政策自动生效或送审 → 规范记录/版本落盘 → 更新索引与星图 → 后续任务可读取。

### 6.3 记忆整理

整理任务负责去重、归纳、过期评估、冲突提案、短期记忆晋升和关系修复。原始来源继续可追溯；摘要丢失适用条件时不得替代原记忆。

记忆任务纳入统一任务服务。本轮用户要求有整理规则，但既有任务管理器仍是三个标签；建议在“Wiki 检查与纠错”标签中增加对象范围 Wiki/记忆，待确认是否改名或独立第四类，不自动分散新增任务面板。

## 7. 与记忆星图的星体映射

### 7.1 分开编码不同含义

- 星体类别：重要性、成熟度与生命周期的组合，采用可解释规则。
- 质量/大小：长期影响、复用价值和业务覆盖的综合“记忆分量”，适度压缩比例，避免大节点遮挡。
- 颜色：当前图例选中的业务分类/领域/工作角色，整图只使用一套颜色语义。
- 光晕/轮廓：选中、冲突或待核实；不是“亮就一定正确”。
- 星团/星系：聚合视图，不自动生成另一条记忆；多领域归属仍只显示一个规范节点。
- 边：有类型、有方向、可追溯的关系；相似度只作为“推断关联”，不能画成已证实依赖。

### 7.2 星体对照

| 星体/结构 | 记忆含义 | 晋升、回退与显示规则 |
|---|---|---|
| 恒星 | 已生效、证据充分、跨任务反复适用的关键事实/方法/核心背景 | 高重要性和适用范围由规则或人工确认；并不因引用量高就自动晋升 |
| 导航恒星（固定标记） | 人工固定的核心原则、项目目标与明确规则 | 保留明显固定标识，规则版本可查；只有对应管理权限能更改 |
| 行星 | 普通、稳定、范围较局部的事实/经验/背景 | 是多数长期记忆的默认形态；不代表低可信或应当删除 |
| 卫星 | 依附某条主记忆、适用条件较窄的细节/补充 | 需有明确 parent/qualifies 关系；轨道只表达该关系，不凭相似度认定“隶属” |
| 彗星 | 当前任务或近期事件中的短期记忆 | 带有效期/衰减提示；可通过审核晋升长期记忆；轨迹表达时间，非真实天文学预测 |
| 星云 | 尚未整理或核实的候选信息群 | 候选层默认单独开关，不混入确定事实；可展开查看原子候选 |
| 双星连线/争议系统 | 同一主题中的互斥结论或重要待决分歧 | 是两条记忆的关系表达；双方各保留证据与状态，不能当成两个同时成立的事实 |
| 白矮星（历史层） | 已被替代但值得追溯的历史记忆 | 默认从当前召回/星图主层隐藏，可打开历史层；保留 supersededBy |
| 星团/星系 | 主题、角色、项目的聚合导航 | 聚合容器，不是权限授权或新事实；计数只包含当前身份可见内容 |

背景星尘仅为装饰，应与可点击的真实记忆节点明显区分。已删除或当前身份无权读取的记忆及其统计不进入场景。

### 7.3 可解释映射

建议把映射定义为版本化策略：先按状态（候选/历史/短期）判形态，再处理显式从属关系，最后根据已确认重要性选择恒星/行星。导航固定标识作为附加装饰，不改写可信度。

每个节点详情显示“为什么是此星体”：如“已确认、重要性高、项目级、跨任务有效”。策略变更生成可追溯版本；人工调整要记录原因，不能通过前端改样式直接改变后端记忆分量。

## 8. 更接近真实星图的呈现

- 恒星采用小型高亮光源、分层柔和光晕与细微色温差；远景保持点状，不把每个节点画成巨大实心球。
- 行星采用低自发光、球面明暗和反射高光；只有聚焦后才展示较详细球面。卫星比主节点小，选中时显示轻量轨道。
- 星云使用低频、低透明的体积感云雾或二维多层近似，避免盖住文字与关系。
- 采用稳定世界坐标、相机透视、深度衰减、前后遮挡、视锥剔除和按距离的细节级别；搜索/筛选不把整片星海重新随机排布。
- 多级缩放：星系总览 → 星团 → 单个记忆系统 → 详情。大规模数据先聚合，按需获取，不让 4,000 节点截断成为长期架构。
- 可切“天文呈现 / 关系分析”：前者突出星体与空间，后者突出节点、边和标签；两者使用同一授权数据和选中对象。
- 关系线默认克制，只强化当前选中节点的必要关系。空间远近表达布局，不宣称为物理距离或精确语义相似度。
- 静止模式作为默认，动效可关闭；支持键盘节点选择与列表替代视图。Canvas 可先验证球体光照/辉光；需要大规模真实材质再评估 WebGL，不预先强制引入重型渲染器。

## 9. 全页面统一视觉系统

主题方向：深空工作台。星图是空间视图，其余页面采用清晰的深色内容面板与统一控件，不把动态星空铺到正文编辑器后面。

| Token 组 | 建议 |
|---|---|
| 背景 | 应用底色 #080D18、面板 #101A2B、抬升面板 #162238 |
| 文字 | 主文 #E8EEFA、次文 #A7B5CD、弱提示 #7586A3；交互内容保证足够对比 |
| 强调 | 冰蓝 #8FB9FF；绿色/琥珀/红色专用于成功/注意/错误 |
| 字体 | 复用项目 Geist + CJK 字体回退；正文 14–16、辅助 12、页面标题 18–22 |
| 几何 | 8px 间距基线；控件 8px 圆角、面板 12px；统一按钮/标签/输入框高度 |
| 交互 | 相同的选中、悬停、禁用、错误、加载和键盘焦点表现；避免只靠颜色识别状态 |
| 布局 | 相同的导航栏、页面标题区、范围/角色选择、内容边界与详情面板模式 |

将现有 index.css 语义变量与星海硬编码色统一到共享 tokens，逐页覆盖对话、Wiki、资料、记忆、星图、任务、审阅、设置和登录。未来明亮主题也使用同一语义 token，不为每页另写配色。

顶栏建议固定显示：当前知识库、当前身份、当前工作角色及访问范围。角色切换在这里发生；记忆页和星图继承同一上下文，并在切换中清除不再有权展示的数据。

## 10. 技术架构与 API 草案

推荐共享记忆服务负责身份、权限、事务与审计，本地/Web/各 Agent 均经 API 访问。多人模式以事务数据库作为规范存储（可选 PostgreSQL，向量为可重建索引）；本机单用户实现可复用仓储协议，但不允许把 JSON 文件直接当跨 Agent 共享后端。

| API | 作用 |
|---|---|
| GET /v1/identity | 当前身份、已授予角色、可用范围 |
| POST /v1/access-contexts | 建立明确角色与项目的访问上下文 |
| POST /v1/memories/search | 授权检索，返回 readSet 与来源/版本 |
| GET /v1/memories/{id} | 读一个获准版本 |
| POST /v1/memory-proposals | 创建/修订/合并等提案，支持幂等键 |
| PATCH /v1/memories/{id} | 授权修订，必须 expectedVersion |
| POST /v1/memory-proposals/{id}/resolve | 审核/合并提案 |
| GET /v1/graph?mode=memory | 授权场景，支持聚合级别、类型与范围 |
| GET /v1/memory-events | 版本事件与客户端投影同步；按范围授权 |

API 名称为草案，需与现有 /api/v1/projects 路由规范统一后实施。MCP 只提供薄适配：identity、roles、context、search/read、propose/revise、graph；不能绕过服务端规则。

## 11. 迁移和实施顺序

1. 落实已确认的角色/项目共享和身份委托语义，固定分层与生命周期规则、字段与星体映射契约。
2. 实现服务端身份/角色上下文、事务存储、ACL 和带版本写入；先做两个 Agent 的读写与冲突验收。
3. 从 workspace.json 导入旧记忆：保留时间、领域和来源；未知可信度/分类不伪造。保留旧 ID 映射，迁移可复核。
4. 接入记忆提案、整理任务、Agent 检索包与引用；再提供 MCP 适配。
5. 星图改用规范记忆数据/权限视图，实现可解释星体映射与多级场景。
6. 应用级视觉 token 与页面壳统一，制作可交互预览后逐页验收。

## 12. 必测验收

- Agent A 在获准项目提交候选，审核后 Agent B 可读；私有记忆和未授权的数量/关系不泄露。
- Agent 同时持有两个角色上下文，互不覆盖；切角色不能提升到未授予权限，撤销授权后后续请求立即失效。
- 两个 Agent 基于同一版本修改，后写方收到冲突；幂等重试不重复创建；旧版本/旧事件不覆盖新投影。
- 同一来源被多个 Agent 转述仍只算一个证据源；高重要但低可信的内容不能自动成为确定结论。
- 有效期、替代、归档、删除对检索、星图、列表一致生效；失败的派生索引可重建。
- 星体形态与详情解释一致；策略版本变更可追踪；多领域节点不复制；背景装饰不可误当记忆。
- 全页面的主题、角色范围、控件状态与键盘焦点一致；角色切换后不残留旧私有内容。

## 13. 已确认决策与后续实施边界

- 默认共享：项目 × 工作角色，私有显式授权。
- 切换：可切工作角色与获授权的权限身份，保持真实操作者可追溯。
- 提供 `policy-v1.json` 与 `access-context-example.json` 作为机器可读契约草案；这些文件不是已经接入服务端的授权实现。
- 当前任务产出为系统设计与视觉设计稿，不宣称既有单用户 workspace.json 已升级成共享数据库。实施时优先做双 Agent 隔离/并发验收，再接正式星图；先完成视觉外壳不能替代授权和事务。
